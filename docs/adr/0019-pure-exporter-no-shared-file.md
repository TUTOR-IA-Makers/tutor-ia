# ADR-0019 — Export renders XML in memory and returns it; no shared questionnaire file

- **Status** Proposed
- **Date** 2026-11-19
- **Deciders** the team (draft written by an agent; a person accepts)

## Context

Step 5 used to append each exported question to one file,
`var/questions/Moodle_Questionnaire.xml`. It read the whole file, counted the
`<question type="coderunner">` already in it to number the new one, and wrote
everything back. Two exports at the same time read the same state, and the
second write dropped the first question without an error. Within one process
the `async def` routes running synchronous code serialised the calls by
accident; a second worker would have removed that protection. ADR-0012 moved
every run's artefacts into the store and left this file out of scope.

G1-8 (#43) asks for the exporter to become a pure function from questions to
XML, numbered by position in the list, touching no shared file. G1-6 (S4) will
build on it to export a teacher's selection of approved questions in one XML.

Three facts constrained the choice:

- **The file was the only way to get the XML out.** Nothing else returned it.
  Whatever replaces it has to give the teacher the XML.
- **Step 5 also completes the run** (ADR-0012). That side effect stays; only the
  shared file goes.
- **`POST /export_moodle_xml_question` answered `{run_id, file_path,
  question_count}`.** The front end does not read the field; curl users and the
  docs do.

## Decision

1. `codeexpert.export.export_questions(questions) -> str` renders a
   `Sequence[ExportQuestion]` into one `<quiz>`, in the order given, numbering
   each question by its 1-based position. It reads and writes nothing. An empty
   list is a `ValueError`.
2. `read_question(workspace)` loads an `ExportQuestion` from a run's artefacts.
   `export_run(workspace)` is step 5: it renders the run's question alone,
   completes the run, and returns `ExportResult(xml, question_count=1)`.
3. Step 5's HTTP response carries the XML in `xml`, which replaces `file_path`.
   The same applies to `export` inside `POST /create_question`.
4. Nothing persists the rendered XML. It is a pure function of artefacts the
   store already holds, so calling step 5 again on a finished run returns it
   again.
5. `CODEEXPERT_QUESTIONS_DIR` is removed. The settings ignore unknown
   variables, so an old `.env` that still sets it keeps working.

## Alternatives considered

| Alternative | Why not |
| --- | --- |
| Keep the shared file, guarded by a file lock | Fixes one host only, keeps a client's question bank in `var/`, and still numbers by what the file happens to hold |
| Store each run's rendered XML as an artefact (`question.xml`) | A second copy of data the store already has, which goes stale when templates or tags change (an approval flips `Nao revisado` to `Revisado`) |
| Keep `file_path` in the response alongside `xml` | It would point at a file that no longer exists |
| Write one file per run under `questions_dir` | Still disk state outside the store, which ADR-0012 moved away from, and nothing would read it |

## Consequences

**Good**

- Concurrent exports cannot interfere: there is no shared state. A test runs
  them in parallel threads and checks every XML is complete.
- Numbering is deterministic. The same list always gives the same XML.
- G1-6 is `export_questions([read_question(ws) for ws in selection])` plus the
  approval check.
- Nothing is written to `var/questions/`, so nothing on the VPS volume grows
  without bound.

**Bad, or costly**

- A breaking change to the step 5 response: `file_path` is gone. A client that
  read it breaks. The repository has none; scripts outside it might.
- No single file collects every exported question any more. Until G1-6, a
  teacher gets one XML per question, and a quiz with several questions takes
  several imports.
- A question generated by `POST /api/v1/questions` has its XML rendered and
  discarded by the job. To get it, call step 5 with the run id.

## Revisit when

Rendering becomes expensive enough to be worth caching (many questions per
export, or a slow template step). Or Moodle needs a stable question number
across exports, for example to update a question it already imported instead of
duplicating it.
